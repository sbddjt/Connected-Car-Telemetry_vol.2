# 2026-10-07 확장·MongoDB 작업 정리

## 현재 상태

- 작업 대상: Connected-Car-Telemetry_vol.2. 원래 Connected-Car-Telemetry 프로젝트는 변경하지 않았습니다.
- 실험용 Python 프로세스와 vol.2 Compose 컨테이너는 종료했습니다. 지도 주소 127.0.0.1:8092는 현재 서비스하지 않습니다.
- 사용자 요청으로 vol.2 data/ 내부의 실험 SQLite 및 WAL/SHM 파일과 telemetry-v2 Compose 프로젝트의 Kafka 3개·MongoDB·Redis 영속 볼륨을 삭제했습니다. 코드·도로/경로 시나리오·실행 로그·검증 보고서는 보존했습니다.
- 다음 실행은 빈 차량 버퍼·빈 Kafka·빈 MongoDB·빈 Redis에서 시작합니다. 이전 운행 데이터를 복구하거나 이어 보내지 않습니다.
- Kubernetes는 Docker Desktop에서 시작을 시도했으나 kubectl에 클러스터가 등록되지 않았습니다. 메모리 부족으로 진행을 보류했고 Kubernetes manifest나 배포 스크립트는 추가하지 않았습니다. Docker Desktop의 Kubernetes 활성화 설정은 사용자가 끄도록 안내했습니다. 꺼졌는지는 확인하지 않았습니다.

## 구현한 데이터 흐름

```text
SUMO 위치·속도 관찰 / 변경·최소 간격 정책으로 기록 선택
  → 차량 SQLite 파일에 묶음 커밋
  → 별도 차량 전송 프로세스가 WebSocket으로 전송
  → 수신 서버가 Kafka에 produce
  → Kafka 최종 성공 확인 후 차량 ACK
  → 확인한 ID만 SQLite에서 묶음 삭제

Kafka 차량 토픽
  ├─ MongoDB 이력 Consumer 그룹: 모든 수신 이벤트 이력, event_id 중복 제거
  └─ Redis 조회 Consumer 그룹: 신호별 최신 위치·속도 유지
       → 조회 API → Leaflet 강남 지도·속도·차량 정보
```

수집·차량 전송·서버 수신·두 종류의 소비는 분리된 프로세스입니다. Kafka 장애 중에도 차량 저장을 계속할 수 있으며, ACK가 없는 기록은 보관·재전송합니다. 차량별 5,000건을 넘으면 오래된 미확인 기록을 삭제·집계하는 제한은 유지합니다. 선택 정책에서 제외한 원본 샘플까지 모두 저장하는 구조는 아닙니다.

## 확장한 구성

| 항목 | 구현 |
|---|---|
| 지도 범위 | 강남역·역삼역·선릉역 주변 실제 OSM 도로망 |
| 로컬 지도 도로 | 3,256개 (이전 304개) |
| 운행 시나리오 | 시뮬레이션 1,800초, 생성 경로 9,000개, 동시 운행 상한 300대 |
| 출발·혼잡 정책 | 0.2초 출발 요청 간격, 60초 이상 출발 지연 차량 제외, teleport 비활성 |
| 차량 SQLite | SHA-256 차량 ID 기준 8개 파일, 같은 수집 단계의 기록은 파일별 한 트랜잭션 |
| 차량 전송 | 샤드마다 1개 프로세스; 차량별 결과 대기 2건, 프로세스별 차량 작업 수 제한 |
| Kafka | 브로커 3개, 차량 토픽 12개 파티션, RF=3·minISR=2 |
| MongoDB 이력 소비 | 같은 그룹의 Consumer 3개, 최대 500건 저장 후 파티션별 오프셋 커밋 |
| Redis 최신 상태 소비 | 별도 그룹의 Consumer 3개, 최대 500건 pipeline/Lua 처리 후 커밋 |
| 관측 지표 | 5초 스냅샷: 차량 수·SQLite 저장·ACK·미전송 수·MongoDB/Redis 처리 속도·지연 |

실제 차량은 각자 독립된 장치의 버퍼를 가집니다. 8개 파일은 한 PC의 SQLite 잠금을 나누는 모방이며 물리적으로 독립된 차량 300대의 CPU·디스크를 재현하지 않습니다. SQLite 파일 간 전역 원자성도 없습니다.

9,000개 경로가 모두 출발·도착하거나 동시에 운행한다는 뜻은 아닙니다. 도로 혼잡과 종료 시점에 따라 실제 출발 수가 줄어듭니다. 실시간 처리 지연이 생기면 시뮬레이션 1,800초의 실제 실행 시간도 늘어납니다.

## MongoDB 저장·장애 정책

일반 컬렉션 telemetry_history의 _id에 event_id를 사용합니다. 원본 JSON, 선택 신호, 차량·실행 ID·순번과 BSON 관측 시각을 보관하고 차량 ID·시각 복합 인덱스를 생성합니다. 재수신 때 달라지는 received_at은 차량 내용의 중복 판정에서 제외합니다.

저장 전체에 성공한 뒤에만 Kafka 오프셋을 커밋합니다. 부분 저장이나 커밋 실패 때 묶음 전체를 다시 처리해도 이미 저장한 같은 이벤트는 추가하지 않습니다. DB 단절·쓰기 확인 실패 시 파티션 소비를 잠시 멈추고 지수 대기하면서 Kafka poll과 재할당 처리를 유지합니다.

실험 중 standalone MongoDB의 retryable write 제약과 중복 키 오류를 확인했습니다. retryWrites=False로 설정하고, 중복 키는 실제 저장된 내용이 같은 경우에만 묶음을 재시도하도록 보완했습니다. 같은 ID에 다른 내용이 있으면 오류로 중단합니다. 마지막 보완은 단위 테스트로 검증했으며 실제 DB 부하를 다시 가한 검증은 보류했습니다.

현재 MongoDB는 단일 노드입니다. j=true로 디스크 저널 확인을 기다리지만 w=majority가 복제본 장애 허용을 제공하지는 않습니다. 운영용 replica set·샤딩·분산 트랜잭션은 구현하지 않았습니다.

MongoDB 실제 장애 검증 결과는 초기 MongoDB 구현에 대한 결과이며 마지막 동시 upsert 보완 이후의 실험 결과로 해석하지 않습니다. 마지막 보완, 샤드 분배, ACK 삭제 묶음·삭제 실패 재시도, 소비 묶음·커밋 실패·재할당은 최종 99개 테스트에 포함됩니다.

수집기의 순간 처리량은 전체 파이프라인 처리 성능을 증명하지 않습니다. 기존 미전송 이력과 신규 수집을 동시에 처리할 때 큐가 쌓이고 MongoDB timeout과 처리 지연이 발생했습니다. 300대가 생성되었다는 사실과 300대 데이터를 지연 없이 지속 처리했다는 사실을 구분합니다.

## 자원 제약과 다음 작업

노트북 RAM은 약 8GB이고 당시 여유 메모리는 약 250MB였습니다. Kafka 3개·MongoDB·Redis·병렬 Python·브라우저와 Kubernetes 시작을 한 PC에 함께 올리기에는 부담이 컸습니다. 데이터 파일 삭제는 디스크 정리이고, RAM 부담은 프로세스·컨테이너 중지로 줄입니다.

다음 작업은 소규모 차량 프로필과 적은 Consumer 수로 다시 시작할 수 있도록 구성하는 것입니다. 이후 자원이 충분한 환경에서 신규 수집·미전송 배출을 함께 측정하고, 처리율·버퍼 증가·Kafka offset lag·지연을 확인합니다. Kubernetes는 컨테이너 수명·배치·확장을 관리하지만 동일 노트북의 CPU·메모리·디스크를 늘려주지는 않습니다.

보류한 작업: Kubernetes 구성, 대규모 지속 성능 검증, 확장 지도 브라우저 검증, MongoDB 이력 조회 API, 운영용 MongoDB 고가용성·샤딩, Kafka offset lag 모니터링.
